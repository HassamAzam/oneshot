## 3. Root causes in detail

### 3.0 The earlier SIGTERM abort (#16, #20, first run)
Three conductors, one run each; two received `SIGTERM` at the same second (almost certainly two
of three loop terminals being closed — closing a terminal sends `SIGTERM` to its foreground
process). The process-wide `AbortController` (`src/index.ts:108`, aborted at `:433`) is passed
straight into the running phase (`src/conductor/runner.ts:776`, `:1036`) and cancels the live
session immediately (`src/conductor/phase.ts:234`).

**Doc/behavior mismatch:** `SUPERVISOR.md` §8 states the *first* `SIGINT`/`SIGTERM` “drains: it
stops claiming and waits for runs to reach a phase boundary.” In reality the first signal
**force-cancels the in-flight phase immediately**. A supervisor trusting the doc will lose
in-flight work they expected to be preserved.

### 3.1 #18 — verify port self-collision + un-reapable wedge
Two compounding bugs:

1. **Port self-collision.** The `local-browser-verify` skill (`skills/local-browser-verify/SKILL.md:16–29`)
   says to bring the app up with a single `PORT=<leased> npm start` and **“Not `manage.py runserver`.”**
   #18's verify agent ignored this: it started Django on the leased port 8000 *and* tried the
   frontend on 8000 → `“Something is already running on port 8000.”` The app never came up.
   (#16's verify did it correctly — frontend on `:3000` — so the behavior is non-deterministic.)

2. **The phase timeout cannot kill a wedged session.** `src/conductor/phase.ts:233` arms
   `setTimeout(() => { timedOut = true; ac.abort(); }, timeoutMin*60_000)`. When it fired at
   ~21:07 the `AbortController.abort()` did **not** terminate the stuck `claude` subprocess
   (pid 65187) — an aborted async iterator that is blocked on a transport/child that never
   yields is never interrupted. Result: the phase promise never settled, the conductor
   deadlocked for **4h15m**, and the run showed a misleading `verify / running` the whole time.

### 3.2 #16 — verify turn cap too small → stale partial → false merge block
`verify` (`config/phases.json`, `name:"verify"`) has `maxTurns: 300`, `timeoutMin: 120`. The
file's own `_why_turns` note already records a 20-case list exhausting a 200-turn cap on run #6,
raised to 300 in response. Run #16's **21-case** list, **plus** in-session environment repair
(Django/webpack bring-up, missing person-history rows, a missing `approved_by` seed value)
**plus** a mid-session context compaction, exhausted 300 turns at 99 of 120 minutes — *after*
every case had been executed and TC-07/TC-13 diagnosed as **defects in verify's own Playwright
driver** (a `.react-datepicker__navigation--next` click-timeout; a leftover MUI dialog
intercepting pointer events) and re-run to PASS. It died on its last to-do (“assemble final
report”) without rewriting the partial `verify.json` from 21:11.

Consequences that made it worse than a simple retry:
- **Stale partial treated as truth.** `verify.json` still said TC-07/TC-13 = `fail` and cited
  `TC-07-fail.png` / `TC-13-fail.png` — **files that do not exist**, while `TC-07-pass.png` /
  `TC-13-pass.png` (mtime 21:27, 16 min later) do. `merge` read the stale array at face value.
- **Capped/incomplete verdicts are recorded as `fail`, not `unknown`.** A driver timeout with
  no assertion mismatch should not be indistinguishable from a real regression.
- **No supported way to force a re-run.** The phase *record* is `ok` (the salvage marked it so),
  so `unblock --phase verify` drops nothing (`KEPT_STATUSES` keeps ok/warned/skipped). There is
  no clean, sanctioned way to make an `ok`-but-stale phase re-run.

### 3.3 #20 — infra egress + a masked deploy failure
The demo box `172.30.1.64` cannot open TCP to `gitlab.arbisoft.com:22` (confirmed by a direct
connect test from the box; GitLab SSH is up from elsewhere, so it is box→GitLab egress
specifically). Two repo bugs turned that into a **silent** wrong-commit deploy:

1. **Masked exit code.** `scripts/deploy-wsai.sh:93` — `git fetch $REMOTE $BRANCH 2>&1 | tail -2`.
   In a pipeline the status is `tail`'s, so a failed fetch looks successful and the script
   proceeds on the box's existing (stale) `HEAD`.
2. **Drift checked against a stale ref.** `scripts/deploy-wsai.sh:205–208` compares `HEAD`
   against `$REMOTE/$BRANCH` — the box's own remote-tracking ref, which is *also* stale when the
   fetch failed — so `DRIFT=0` and it reports `ONESHOT_RESULT=ok` / `HTTP=200` while running the
   wrong commit (ticket-5's merge from 2026-08-27, not #20's `3d9cfb45`).

### 3.4 Orphaned-process litter (cross-cutting)
A killed/crashed run leaves its dev servers and helpers running: `reapPortServer`
(`src/lib/worktrees.ts:122`) only runs on **graceful** port release, so a `SIGTERM`/`SIGKILL`ed
run orphans them. At cleanup time this machine held: 2 orphan Django servers (`:8000`, `:8001`),
6× `tail -f /dev/null`, and a `jest --updateSnapshot` wedged for **6 hours**. Minor separate bug:
verify used `setsid` (`state/runs/16/npm-start2.log`: `command not found: setsid` — absent on macOS).

## 4. Repository changes to make

Ordered by leverage. Each is independent.

### P0 — a phase timeout must actually kill the process (`src/conductor/phase.ts`)
The single worst failure mode: a wedged session can outlive its own timeout indefinitely and
deadlock its conductor. When the timeout fires, escalate beyond `AbortController.abort()`:
after a short grace period, **`SIGKILL` the SDK child process (and its process group)**. Track
the child pid and force-kill it so the phase promise always settles.

### P1 — verify must not leave a stale partial that downstream reads as truth
- Write `verify.json` **atomically at the end**, or mark a partial explicitly incomplete
  (`"complete": false`) and have `merge` refuse to consume an incomplete verify as `fail`.
- Record capped/timed-out cases as **`unknown`/`blocked`**, never `fail`, unless there is an
  actual assertion mismatch. Only a real regression should block `merge`.

### P1 — deploy must fail loudly on a failed fetch (`scripts/deploy-wsai.sh`)
- Line 93: drop the `| tail -2` mask (or `set -o pipefail` + check `${PIPESTATUS[0]}`); abort the
  deploy if `git fetch` fails instead of proceeding on stale `HEAD`.
- Lines 205–208: assert the **deployed SHA equals the target merge SHA**, not that `HEAD` matches
  a possibly-stale cached ref. Fetch-failure must be `ONESHOT_RESULT=fail`, not `ok`.

### P2 — verify port model: make it deterministic (`skills/local-browser-verify/SKILL.md` + phase)
Either (a) enforce the single-origin `PORT=<leased> npm start` model and hard-fail if the agent
starts `manage.py runserver` on the leased port, or (b) lease **two** ports (backend + frontend)
and hand both to the agent explicitly. #18 vs #16 diverging on this proves the current guidance
is not reliably followed.

### P2 — raise the verify budget (`config/phases.json`, `name:"verify"`)
`maxTurns: 300 → 450`, `timeoutMin: 120 → 150` (per the run-#16 remediation). The cap has now
been exceeded by real, non-looping work twice (runs #6 and #16). Consider scaling `maxTurns`
with case count instead of a fixed number.

### P2 — reap a run's servers on any termination (`src/lib/worktrees.ts` / conductor shutdown)
Call `reapPortServer` (and kill anything under the run's worktree) on **every** run exit —
including abort/kill paths — or add a startup sweep that kills dev servers/`tail`/jest left under
`oneshot-wt/*`. Also replace `setsid` (absent on macOS) in the verify bring-up.

### P3 — support forcing an `ok` phase to re-run (`scripts/unblock.ts`)
Add an explicit `--force-phase <name>` that drops an `ok` record **and** its artifact, so a
stale-but-`ok` phase can be legitimately re-run without hand-editing `run.json`.

### P3 — fix the shutdown doc or the shutdown behavior (`SUPERVISOR.md` §8 / `src/index.ts`)
Either make the first signal genuinely drain to a phase boundary, or correct §8 to say the first
signal force-cancels the in-flight phase immediately. Today they disagree.
