# Script Writing Standards

Rules for standalone scripts in this repo — i.e. anything under `scripts/`, anything generated by `/fix-data`, `/investigate-data`, or any one-off Django shell script. These rules are MANDATORY for every team member; consistency here matters because the CEO and other engineers run these scripts on prod and on their local DBs.

These rules are additive to `django-backend-standards` and `python-linting` — those still apply.

---

## Where scripts live — `tmp_scripts/`, never `scripts/`

**All ad-hoc scripts go into `tmp_scripts/`** — fixes, investigations, seeds, diagnostics, load-tests, anything one-off. The directory is `.gitignore`d so these never accidentally end up in MRs.

- `scripts/` is for tracked utility code that ships with the repo (rare — usually empty in feature branches).
- `tmp_scripts/` is the working drawer for everything else. Everyone has their own untracked scripts there.
- **Exception**: if the utility deserves to ship with the repo, build it as a Django **management command** under `apps/<app>/management/commands/<name>.py` — that's the canonical place for tracked, repeatable operations. Management commands get tests, lint, code review, and `python manage.py <name>` ergonomics.

When asked to write any "script", default to `tmp_scripts/<name>.py` unless the user explicitly says it should be tracked or it should be a management command.

**If `tmp_scripts/` doesn't exist, create it first** (`mkdir -p tmp_scripts`). The directory is `.gitignore`d, so it won't exist on a fresh clone — that's expected. Just `mkdir` and proceed; no commit, no tracking.

---

## Every script MUST be Django-shell-runnable — no bootstrap boilerplate

**ANY** script written under this skill — whether for `/fix-data`, `/investigate-data`, a seed, or any other ad-hoc utility — MUST be runnable inside an active Django shell with **no setup boilerplate**. The CEO and engineers run these via:

```bash
python manage.py shell < tmp_scripts/your_script.py
```

…or by pasting the file's contents directly into a `python manage.py shell` session. Both paths assume Django is **already set up** in the runtime — apps are loaded, models are importable, the ORM is alive.

### Forbidden in every script

- `os.environ.setdefault("DJANGO_SETTINGS_MODULE", ...)` — Django is already configured.
- `import django; django.setup()` — already done by the shell.
- `sys.path.insert(0, ...)` — the project root is already on `sys.path`.
- `if __name__ == "__main__":` guards — there is no `__main__`; the file is `exec`'d in the shell, not run as a top-level module.
- `argparse` / `sys.argv` parsing — no CLI args; configuration is via uppercase scope constants at the top of the file (see "Scope as uppercase constants" below).
- A `def main(): ...` plus a final `main()` call. Just put the logic at module level (or extract helpers and call them at the bottom).

### Required shape

```python
"""Top-level docstring describing what the script does, who runs it, and how."""

from collections import Counter
from datetime import timedelta

from django.utils import timezone

from apps.project_logs.models import PersonWeekLog, ProjectTask

# ===== Scope =====================================
LOOKBACK_DAYS = 730
TOP_N = 20
# =================================================


def _do_the_work():
    """All real logic goes in helpers like this — keeps module-level code thin."""
    cutoff = timezone.now().date() - timedelta(days=LOOKBACK_DAYS)
    ...


_do_the_work()
```

That's it. No bootstrap, no main-guard, no CLI parsing. The trailing `_do_the_work()` line is what makes `python manage.py shell < scripts/foo.py` actually run the helper after defining it.

### Why this matters

- **CEO friction.** The CEO runs scripts via `python manage.py shell < script.py` or by pasting into the shell. Boilerplate that re-bootstraps Django either silently no-ops (best case) or breaks (worst case — `django.setup()` called twice on certain configurations raises).
- **Lint noise.** Standalone-script Django bootstrap forces an `E402` exemption (imports after `django.setup()`), which leaks `# noqa: E402` or per-file ignores in `.flake8`. None of that is needed if we just write shell-runnable scripts.
- **Consistency.** Every script in the repo runs the same way — one mental model, one run command, one debugging story.

### Lint configuration

`.flake8` and `.pylintrc` should NOT carry `scripts/`-specific exemptions for E402 or import-order issues — those exemptions exist only because the boilerplate forced them. With the shell-runnable shape, regular flake8/pylint rules apply cleanly. If you encounter such an exemption while editing the skill or writing a script, propose removing it.

### When the "script" really does need to be a CLI tool

Rare. If a request is genuinely for a CLI utility (cron job, CI helper, something that doesn't run inside a Django shell), it should be a **Django management command** under `apps/<app>/management/commands/<name>.py`, not a `scripts/` file. Management commands have their own conventions and `BaseCommand` boilerplate that's standard across Django. They are NOT the subject of this skill.

If you're unsure whether a request is "script" or "management command", ask the user before writing.

## Test/sentinel users — email domain MUST be `@example.com`

This rule applies **only when the email is fabricated** — i.e. you're creating a User that doesn't represent a real person, just a placeholder for testing / seeding / a sentinel row that will be cleaned up later.

When a script needs to create a fabricated/test/sentinel `User` (e.g. so it can attach a `Person` to it for seeding fake project logs / payroll data / etc.), the email **must** end with `@example.com`.

**Why:** `@example.com` is reserved by IANA (RFC 2606) and will never deliver mail. Other made-up TLDs (`@example.invalid`, `@test`, `@local`) are not a stable convention across the team and make it hard to grep for "all the rows my seed scripts created" later. Standardising on `@example.com` means every script-generated test user is identifiable by a single grep, and we don't risk anyone accidentally setting up a real `@example.invalid` mailbox.

**How to apply:**

```python
# OK — fabricated email for a test/sentinel user
test_user = User.objects.create(
    username=f"test-seed-{suffix}",
    email=f"test-seed-{suffix}@example.com",
)

# NOT OK — never invent a different TLD
User.objects.create(email=f"test-{x}@example.invalid")     # forbidden
User.objects.create(email=f"test-{x}@test.local")          # forbidden
User.objects.create(email=f"test-{x}@arbisoft.com")        # never use a real domain for fabricated users
```

The same rule applies anywhere a script writes a fabricated email address — `personal_email`, secondary contacts, etc.

**When NOT to apply:** if the script is creating a real user on prod (for example, a `/fix-data` script that has to provision a missing `User` row for an actual employee, with the employee's real email supplied by the user), use the **real email**. Do NOT rewrite real prod emails to `@example.com`. The `@example.com` rule is for fabricated/test rows only — if the user provides a proper email for a real person, that's the email the script writes.

## Scope as uppercase constants at the top

Every script must declare its filtering / target IDs as uppercase constants at the top of the file, above the imports if possible (or immediately below them). This makes it trivial for the operator to change the scope without reading the script.

```python
# ===== Scope =====================================
PERSON_ID = 2816
OLD_PERSON_TEAM_ID = 14388
NEW_PERSON_TEAM_ID = 15151
START_DATE_STR = "2025-12-17"
# =================================================
```

Don't bury IDs deep in functions.

## Don't add DRY_RUN on your own — ask first

Do **not** add a `DRY_RUN` flag (or any other plan/preview mode) to a script unless the user explicitly asks for it. This applies to **every** script — including ones produced by `/fix-data` and `/investigate-data`.

**Why:** the workflow in this team is "team tests the script locally on seeded/staging data, then hands a single-run script to the CEO." Asking the CEO to run the same script twice (once with `DRY_RUN=True` to preview, once with `DRY_RUN=False` to apply) is not viable — the CEO doesn't have time for a two-pass run, and any review needs to happen before the script reaches him.

If you think a script genuinely needs a DRY_RUN (e.g. you've been asked to write something that the CEO will iterate on directly, or the user wants a peek-then-apply flow), ask before adding it:

> "Do you want me to add a DRY_RUN flag so you can preview the plan first?"

Add it only if they confirm.

Investigation scripts (read-only) don't need a `DRY_RUN` flag — they don't mutate. Say so in the docstring instead.

## Wrap every mutating run in a single transaction

```python
with transaction.atomic():
    ... apply changes ...
    failures = _verify(...)
    if failures:
        raise RuntimeError("Verification failed")
```

If verification finds anything off, raise — the transaction rolls back automatically. Never mutate without a verification pass.

## Sentinel naming for seeded fixtures

Seed scripts (e.g. `scripts/seed_*`) that create test data should mark the fixture with a sentinel value the script can find again later for cleanup. The convention is a `full_name` prefix of `ZZZ Test ` for `Person`, and similar `ZZZ Test ` / `test-` prefixes for other models.

Re-running a seed script must be safe — it should wipe its previous fixtures (matched by sentinel) before creating new ones, and support a `WIPE_ONLY = True` mode for cleanup.

---

## Standalone, no app-code edits

Scripts under `scripts/` must not modify code in `apps/` or `common/`. If the script depends on a code change, that change goes in a separate commit / MR. Scripts are meant to be cherry-pickable and runnable in isolation.

---

## Linting still applies

Run `flake8` and `pylint` on every script just like any other `.py` file (see `python-linting` skill). Migrations may be excluded; scripts are not.

## Delivering a script to someone — use `slack-attach`

When you need to send a script for someone else to run on prod, the standard delivery path is the user's local CLI helper at `~/.local/bin/slack-attach`. It uses Slack's `files.upload_v2` to attach the actual `.py` file in a DM, with an `initial_comment` describing what the script does.

```bash
slack-attach <user> <path-to-script.py> --message "<one-line summary + run command>"
```

Where `<user>` is one of:
- Slack user ID (`Uxxxxxxxx`) — fastest
- email (`first.last@arbisoft.com`)
- username (`first.last`) — slow, paginates `users.list`

Token: read from `SLACK_MCP_XOXP_TOKEN` (or `SLACK_USER_TOKEN`). Required user-token scopes:
- `files:write`, `im:write`, `users:read`, `users:read.email`

Do NOT fall back to GitLab snippets / Slack Canvas / pasting code into a message unless the CLI is unavailable — sending a real file attachment is what the recipient expects, and `initial_comment` keeps the run instructions stuck to the file forever.

**Message format for a /fix-data delivery:** start with a one-sentence "What it does", then the literal run command in backticks, then any caveats. Don't mention `DRY_RUN` (we don't ship those — see the no-DRY_RUN rule above).

**If the upload fails with `missing_scope`:** the user's xoxp token doesn't have `files:write` — they need to add the scope at api.slack.com/apps and reinstall. Surface the missing scope and stop; don't silently fall back to a worse delivery method.

**Cache caveat:** `slack-attach` reads the token from the env var present at process start. If the user updates `~/.zshrc`, your existing Bash subshell still has the old token. Pick up the new value via:

```bash
NEW=$(zsh -ic 'printf %s "$SLACK_MCP_XOXP_TOKEN"' 2>/dev/null)
SLACK_MCP_XOXP_TOKEN="$NEW" slack-attach …
```
